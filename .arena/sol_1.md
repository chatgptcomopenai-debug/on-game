# «Избранный» — план реализации (подход «прагматик»: быстрее до играбельного, меньше рисков)

## 0. Главные решения в одной строке
Vanilla JS (ES-модули, без сборщика) + Canvas2D + PeerJS (P2P, хост решает всё) + публичный PeerJS-брокер + TURN-фолбэк. Хостинг на GitHub Pages. Никакого своего сервера, никакого фреймворка, никакого npm.

## 1. Сеть
**Выбор: P2P со звездой, хост решает всё (host-authoritative), на PeerJS.**
- Создатель комнаты — хост. Код комнаты: 5 символов (A–Z без I/O + 2–9), peerId = `izbr-<код>`. Клиенты подключаются через `peer.connect('izbr-'+код)`.
- Сигналинг — бесплатный `0.peerjs.com`. Риск: его недоступность → в конфиге один флаг для своего брокера (`peerjs-server` на бесплатном Render/Fly), но в MVP он не нужен.
- **NAT/мобильный интернет:** у операторов (CGNAT, симметричный NAT) напрямую часто не соединиться. Сразу передаём в `iceServers` STUN от Google + бесплатный TURN (Metered/ExpressTURN, free tier, ключ в config.js). Без TURN примерно 20–30% мобильных пар не соединятся — это главный риск, закрываем на 1-й день.
- DataChannel: `reliable: false` (неупорядоченный, без повторов) для снапшотов/ввода; второй канал `reliable: true` для событий (старт раунда, смена Избранного, счёт, чат-эмодзи нет).
- **Уход хоста:** НЕ делаем миграцию хоста в MVP (дорого и с багами). Делаем так: хост держит экран активным (Wake Lock API), при потере хоста клиенты видят «Хост вышел» → кнопка «Новая комната» (бывший первый клиент становится хостом с новым кодом, счёт обнулён). Ушёл клиент — хост просто убирает его; если он был Избранным, сила переходит случайному живому охотнику.
- Почему не WebSocket-сервер: нужен хостинг, cold start на бесплатных тарифах 30–60 с, дольше разработка. P2P на 3–6 игроков у хоста — это ~5 исходящих потоков по ~3 КБ/с, телефон справится.

## 2. Рендер
**Canvas2D, без движка.** Phaser — 1 МБ и своя модель жизненного цикла, которую сеть всё равно ломает; Pixi — WebGL быстрее, но для ~6 игроков + ~60 частиц Canvas2D хватает с запасом и проще отлаживать. Одна логическая арена 1600×900, масштаб `ctx.setTransform` под экран, DPR ограничен значением `min(devicePixelRatio, 2)`.

## 3. Структура кода
```
index.html        — canvas, оверлеи меню (DOM), подключение main.js
style.css
src/
  config.js       — ВСЕ числа баланса, сетевые константы, ICE-серверы
  main.js         — экраны: меню → лобби → игра → итоги
  net.js          — PeerJS: host()/join(code), send, onMessage, пинг
  sim.js          — чистая симуляция: step(state, inputs, dt) (запускается только у хоста)
  powers.js       — 4 силы: {cast(state,p), update(...)}
  match.js        — раунды, таймер, очки, смена Избранного
  render.js       — отрисовка + неон-кэш
  fx.js           — частицы (пул)
  input.js        — джойстик + кнопки (Pointer Events, multitouch)
  interp.js       — буфер снапшотов, интерполяция
lib/peerjs.min.js — вендорно, конкретная версия (1.5.4)
```
**Цикл:** хост: `setInterval`-аккумулятор, фиксированный тик **30 Гц** (dt=33.3 мс) для `sim.step`; рендер у всех в `requestAnimationFrame`. Хост тоже рендерит через интерполяцию своего же состояния (одинаковый путь кода = меньше багов). Фоновая вкладка у хоста = игра на паузе: предупреждаем в лобби.

## 4. Синхронизация
- **Ввод клиента:** каждый кадр отправляет только при изменении, но не реже 20 Гц: `{seq, jx, jy (int8), btn-биты}`. ~8 байт → JSON допустим, в MVP без бинарщины.
- **Снапшоты:** хост шлёт 15 Гц полное состояние (6 игроков × {id,x,y,hp,state,flags} + снаряды). Это меньше 1 КБ, дельта-сжатие не нужно.
- **Интерполяция:** клиенты рисуют чужих с задержкой 100 мс (между двумя снапшотами), при потере экстраполируем не больше 150 мс.
- **Предсказание:** только движение своего персонажа (локально применяем тот же `move()` из sim.js), сверка с сервером: если расхождение больше 40 px — жёсткий snap, иначе плавная подтяжка 20%/кадр. Без реконсиляции с переигрыванием ввода — для 90-секундной казуалки достаточно.
- **Попадания** считает только хост («выигрывает хост»). Атаки клиента рисуются мгновенно как эффект (вспышка), урон — по снапшоту. Ожидаемая задержка 60–150 мс приемлема, кулдауны маскируют задержку.

## 5. Неон без потерь FPS
- **Никакого `shadowBlur` в горячем цикле** (главный убийца FPS на Android). Вместо него: при старте пререндерим «свечение» каждого спрайта (круг, кольцо, снаряд) в offscreen-canvas с shadowBlur один раз, потом `drawImage`.
- `globalCompositeOperation = 'lighter'` для частиц/свечения.
- Фон: сетка заранее нарисована в отдельный canvas, раз в кадр — один drawImage.
- Пул частиц максимум 150, урезаем вдвое при среднем FPS < 45 (авто-качество).
- Палитра: фон #07070f, охотники — циан #3ef, Избранный — по силе (Пламя #f60, Молния #ff3, Лёд #8ef, Гигант #f3f).

## 6. Баланс (все числа в config.js; N — число игроков, H=N−1 охотников)
**Охотник:** HP 100, скорость 260 px/с, Атака — короткий бластер: урон 8, снаряд 700 px/с, КД 0.35 с. Рывок: 220 px за 0.15 с, КД 3 с. Смерть → респаун через 3 с в случайном углу.

**Избранный (база):** HP = 250 + 150·H (3 игрока → 550, 6 → 1000), скорость 240, радиус ×1.5. Регенерация отсутствует. Кнопки: Атака (своя для силы), Ультимейт (КД ниже), Рывок (как у охотника).
Урон охотников по Избранному ×(1 + 0.05·(H−2)) — не нужен, масштабирует HP. Таргет: средний охотник наносит ~22 DPS при 80% точности → 5 охотников ≈ 110 DPS → 1000 HP ≈ 9 с чистого огня; с учётом уклонений/смертей Избранный живёт 30–60 с. Тестируем и правим только `HP_PER_HUNTER`.

| Сила | Атака | Ультимейт (КД) | Пассивка |
|---|---|---|---|
| Пламя | конус 120°, 260 px, 30 урона/с, держать | Огненное кольцо R 220: 45 урона + горение 10/с 3 с (8 с) | след огня 15 урона/с |
| Молния | луч до 500 px, 22 урона, КД 0.5 с | Цепь: бьёт ближайших 3 по 35 (7 с) | скорость 290 |
| Лёд | 3 осколка веером, 14 каждый, КД 0.6 с | Заморозка R 200: стоп 1.5 с + 20 урона (9 с) | замедление попаданием −30% 1 с |
| Гигант | удар R 140, 40 урона, КД 0.9 с | Прыжок-сокрушение в точку 350 px: 60 урона R 180, отброс (10 с) | HP ×1.3, скорость 210, урон по нему −15% |

**Очки:** охотник: 1 за каждые 50 урона по Избранному, +10 за добивание. Избранный: +1 за каждые 3 с жизни в роли, +5 за убийство охотника. Победа в раунде: если Избранный дожил до конца раунда — +15. Добивший становится Избранным (новая случайная сила) прямо в раунде, HP пересчитывается, 1.5 с неуязвимости.
**Раунд:** 90 с, в начале каждого раунда Избранный — случайный (в 1-м) или текущий лидер-охотник по очкам не определяем — проще: случайный игрок, который ещё не был стартовым Избранным. 5 раундов → экран итогов (таблица, MVP «Самый долгий Избранный»).

## 7. MVP — 7 шагов (каждый заканчивается чем-то, что можно запустить на телефоне)
1. **Каркас + управление:** index.html, canvas в ландшафте (оверлей «поверни телефон»), fullscreen по тапу, джойстик + 3 кнопки, один кружок бегает по арене локально. Деплой на Pages с первого дня.
2. **Сеть:** net.js, создание/вход по коду, лобби со списком, хост стартует; хост гоняет sim 30 Гц, клиенты шлют ввод, получают снапшоты, интерполяция. Проверка на двух телефонах через 4G — сразу TURN.
3. **Бой охотников:** бластер, рывок, HP, смерть/респаун, предсказание своего движения.
4. **Избранный:** выбор, HP-скейлинг, одна сила (Молния — проще всего), передача силы добившему.
5. **Остальные 3 силы** + пререндеренный неон, частицы.
6. **Матч:** таймер 90 с, 5 раундов, очки, экран итогов, «Ещё раз».
7. **Полировка и устойчивость:** обработка ухода игроков/хоста, Wake Lock, авто-качество, звук (WebAudio-бипы, опционально), плейтест на 3–6 реальных телефонах и правка config.js.

## 8. Риски и что с ними
- **Не соединяются по 4G** → TURN с первого дня; при ошибке показ «не удалось подключиться, попробуйте Wi‑Fi».
- **Хост свернул браузер / ушёл** → игра встаёт; честно сообщаем, быстрый рестарт комнаты. Миграция хоста — после MVP.
- **Падение 0.peerjs.com** → флаг на свой брокер.
- **iOS Safari:** нет Fullscreen API на iPhone → используем `100dvh`, подсказка «Добавить на экран Домой»; блок жестов `touch-action:none`; аудио только после тапа.
- **Читерство хоста** — не решаем (друзья по коду).
- **Слабые телефоны** — Canvas2D без shadowBlur + DPR≤2 + авто-качество.

Явно вырезано из MVP: аккаунты, матчмейкинг, миграция хоста, бинарный протокол, реконсиляция с перепроигрыванием ввода, спрайты/ассеты, сборщик.
